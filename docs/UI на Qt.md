# UI на Qt

> Оригинальная серия: [[Package Browser]]

## Зачем такое устройство интерфейса

Приложению нужно показывать плотные списки и деревья: сотни окружений и тысячи пакетов с сортировкой и фильтрацией. Для таких данных у Qt Widgets есть зрелые готовые классы (`QTreeView`, `QTableView`, `QSortFilterProxyModel`), поэтому для MVP выбран Qt 6 Widgets с Model/View. QML имеет смысл, если понадобится стилизованный интерфейс, но на сами данные это не влияет: модели пишутся один раз и подходят обоим.

Главная задача интерфейса — сделать различие «глобальное и локальное» видимым с первого взгляда, а не прятать его в колонке `scope`.

## Раскладка окна

```text
+------------------------+--------------------------------------------+
| Дерево окружений       | Таблица пакетов выбранного узла            |
|                        |  имя | версия | менеджер | окружение | scope|
| v Глобальное           |                                            |
|   v Python (System)    |                                            |
|   > npm (System)       |                                            |
| v Проекты              |                                            |
|   v ~/work/app         +--------------------------------------------+
|     .venv  (pip)       | Детали пакета: путь, где ещё установлен    |
|     node_modules (npm) |                                            |
+------------------------+--------------------------------------------+
```

- Узел **Глобальное** — окружения со `scope` `System` и `User`, сгруппированные по экосистеме и менеджеру.
- Узел **Проекты** — по одной ветке на каталог `Project`, внутри него окружения (`.venv`, `node_modules`, …) с бейджем их `ToolInstance` и версией.
- Переключатель «Все пакеты» — плоский список по всем окружениям с колонками `имя`, `версия`, `менеджер`, `окружение`, `scope`. Это ответ на вопрос «где у меня установлен `requests` и каких версий», из [[Package Browser]].
- В MVP список плоский: рёбер зависимостей нет ([[Решения и roadmap]]).

## Модели представления

| Класс | База Qt | Роль |
| --- | --- | --- |
| `EnvironmentTreeModel` | `QAbstractItemModel` | дерево «глобальное / проекты»; статус окружения (ok, stale, error, untrusted) как `Qt::DecorationRole` |
| `InstallationTableModel` | `QAbstractTableModel` | пакеты одного окружения или всех; подгрузка частями через `canFetchMore` / `fetchMore` |
| `PackageFilterProxy` | `QSortFilterProxyModel` | фильтры по тексту, экосистеме, менеджеру и `scope` |
| `PluginListModel` | `QAbstractListModel` | экран плагинов: состояние, ошибки, переключатель «включён» |
| `SettingsTab` | `QWidget` | экран настроек: один список папок сканирования (project roots) с чекбоксом «доверенная» у каждой (trusted), глубина сканирования; кнопка «Save Settings» пишет всё в `AppSettings` (INI-файл) и запускает скан. Изменения накапливаются и применяются только по кнопке — авто-сканирования на каждую правку нет |

## Потоки и взаимодействие с ядром

`CatalogService` — фасад ядра и единственная точка контакта UI. Интерфейс никогда не говорит с плагинами напрямую.

| Что | Как |
| --- | --- |
| Запросы UI → ядро | `listEnvironments(filter)`, `listInstallations(envId, query)`, `findPackage(name)`, `rescan(scope?)` |
| События ядро → UI | сигналы `environmentsChanged`, `installationsChanged(envId)`, `scanProgress`, `pluginStateChanged` |
| Потоки | `CatalogService`, опрос провайдеров и запись в SQLite — в рабочем потоке; UI-поток читает только через сигналы и слоты |
| Процессы провайдеров | запускаются через `QProcess` |

> [!note]
> У Qt SQL одно соединение `QSqlDatabase` нельзя передавать между потоками, поэтому каждый поток открывает своё соединение с уникальным именем ([[Хранилище и кэш]]).
