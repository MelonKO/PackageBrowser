# Решения и roadmap

> Оригинальная серия: [[Package Browser]]

## Зачем эта заметка

Здесь собраны решения, которые легко забыть или оспорить позже: почему выбран именно такой стек, какие альтернативы рассматривались, что принято по открытым вопросам, какая лицензия и в каком порядке собирать приложение.

## Trade-off'ы

| Решение | Выбрано | Альтернатива | Почему | Цена решения |
| --- | --- | --- | --- | --- |
| Язык и UI | C++ / Qt 6 | Java (JavaFX или Swing) | базовый стек разработчика; `QProcess`, Qt SQL и Model/View уже есть | нет готового TOML-парсера и JSON-RPC (нужна сторонняя библиотека или свой тонкий слой); условия лицензии и способ деплоя проверить до распространения |
| Плагины | гибрид: манифест + внешний процесс | только DLL, только манифесты, только процессы | простые случаи не требуют кода, сложные не упираются в выразительность манифеста | два пути выполнения надо тестировать; декларативный DSL тянется к разрастанию, его нужно держать маленьким |
| Хранилище | SQLite-кэш | только память, JSON-файлы | мгновенный старт UI, поиск «где ещё установлен X» одним запросом | ещё один слой и риск расхождения с диском, закрытый пересборкой кэша |
| Чтение project-local окружений | разбор файлов без запуска инструмента | вызов `pip list` из venv | безопаснее и быстрее | своя логика разбора форматов может расходиться с тем, что покажет сам менеджер; проверять на новых версиях |
| Граница «проект» | вычисляемая группировка | проект как сущность с жизненным циклом | не нужно синхронизировать состояние и дублировать истину | для монорепо с десятками окружений группировку по каталогу можно уточнить явными правилами |

Если вместо C++/Qt выбрать Java: модель данных, манифесты и протокол остаются без изменений; меняются только реализация сервисов (`ProcessBuilder`, JDBC, модели таблиц) и способ поставки (встроенный runtime вместо нативного бинарника). Граница между ядром и плагинами процессная, поэтому язык ядра не влияет на плагины. Это общее сравнение, без замеров на конкретном окружении.

## Решения по открытым вопросам

| Вопрос | Решение |
| --- | --- |
| Менеджеры в MVP | pip, npm и vcpkg. Остальные (conda, pipx, poetry и др.) подключаются позже плагинами; модель должна их выдержать, но это не проверялось |
| Платформы | Windows и Linux; macOS вне MVP, потому что его нечем тестировать; в архитектуру ничего, что делало бы его добавление невозможным, не закладываем (разные пути к инструментам уже вынесены в манифесты) |
| Список пакетов | плоский список + рёбра зависимостей на этапе 4. Параметр `withDependencies` в контракте необязателен; таблица `dependency` заполняется для провайдеров, которые умеют отдавать рёбра (vcpkg через SPDX), остальные честно остаются плоскими | граф зависимостей — этап 4 |
| Корни проектов | только заданные вручную, без автообхода домашнего каталога; лимит глубины остаётся |
| Распространение | open source через репозиторий на GitHub; лицензия приложения — GPLv3 (см. ниже) |
| Объём MVP | этапы 1–3 из roadmap |

## Лицензия: GPLv3

Для открытого проекта у Qt есть три пути, и коммерческая лицензия среди них не нужна.

| Вариант | Лицензия приложения | Условия | Когда подходит |
| --- | --- | --- | --- |
| A. GPLv3 (**выбран**) | GPLv3 | производные работы тоже под GPL; доступны все модули Qt | проще всего юридически |
| B. LGPLv3 для Qt | любая совместимая, включая MIT и Apache | динамическая линковка и выполнение условий LGPL | нужна более свободная лицензия приложения |
| C. Коммерческая лицензия Qt | любая | платная | закрытые продукты |

Смешивать Community Edition и коммерческую лицензию Qt в одном проекте нельзя.

**Что даёт вариант A.** Отдельных условий LGPL (динамическая линковка, возможность подмены библиотек Qt) выполнять не нужно, и можно использовать любые модули Qt, включая те, что в открытой версии доступны только под GPLv3.

**Для справки, что потребовал бы вариант B:**

- динамическая линковка (DLL или `.so` рядом с приложением), статическая усложняет условия;
- тексты лицензий GPL и LGPL и заметное уведомление, что используется Qt под LGPL;
- исходники использованной версии Qt (даже без изменений);
- возможность заменить библиотеки Qt на свою сборку.

**GPL-only модули.** По документации Qt, в открытой версии только под GPLv3 доступны, в частности, Qt GRPC, Qt HTTP Server, Qt Graphs и Qt Quick 3D. Для этого проекта они не нужны: ядро и интерфейс строятся на Qt Core, Qt Widgets и Qt SQL.

> [!warning]
> На странице документации Qt явно не названо, под какими лицензиями Core, Widgets и SQL; по моим знаниям они доступны под LGPLv3. Перед выпуском сверьтесь со страницей лицензий той версии Qt, которую используете. Я не юрист.

**Что нужно делать при выпуске под GPLv3:**

- вместе с бинарниками на GitHub нужны текст лицензии и исходники (для открытого репозитория это просто);
- сторонние плагины-процессы общаются с ядром только через JSON-RPC и по сути являются отдельными программами; как правило, GPL на них не распространяется, но точную границу я не проверял. В документации плагинов стоит отметить, что их лицензия не обязана совпадать с GPLv3;
- лицензии подключаемых библиотек (например, парсера TOML) нужно сверять при добавлении: насколько я знаю, MIT-лицензии совместимы с GPLv3, но это нужно подтвердить на странице каждой библиотеки.

Лицензионные условия Qt разобраны выше в разделе «Лицензия: GPLv3».

## Roadmap

Порядок сборки: сначала доказать модель «глобальное отдельно от локального» на одном менеджере, и только потом наращивать плагины. Каждая фаза закрывается проверяемым критерием.

1. **Скелет.** Доменная модель, `CatalogService`, SQLite, `IProvider`, встроенный провайдер pip, таблица в UI. *Критерий:* системный pip и pip из venv показаны как два окружения с разными наборами пакетов.
2. **Обнаружение и манифесты.** Сканер корней с trust, декларативный адаптер, npm как первый менеджер без кода плагина. *Критерий:* новый CLI-менеджер подключается одним `plugin.toml`.
3. **Процессные провайдеры.** JSON-RPC по stdio, жизненный цикл и карантин, vcpkg как первый менеджер с логикой, экран плагинов. *Критерий:* упавший провайдер не влияет на остальные окружения.
4. **Глубина.** Рёбра зависимостей (таблица `dependency`, vcpkg через SPDX), поиск «где ещё установлен пакет», `inheritsFrom` (pip-venv с `include-system-site-packages`), старт из кэша. *Критерий:* на реальной машине старт из кэша показывает данные до завершения фонового скана. Реализовано в ветке `feature/stage4-depth`; точный порог «кэш быстрее полного скана» измерить после накопления данных кэша на реальной машине.
5. **Действия.** Расширение контракта операциями `plan` и `apply`.

> MVP = этапы 1–3.

## Будущие действия: install, update, remove

Цель — исключить классическую ошибку «установили не в то окружение». Поэтому:

- цель действия всегда явный `EnvironmentId`;
- выполняется оно `ToolInstance` этого окружения, а не тем, что первым нашлось в `PATH`;
- порядок: `plan` (показать изменения, подтверждение) → `apply` с прогрессом и отменой → пересчёт `fingerprint` и пересканирование именно этого окружения;
- для `System` нужны повышенные права, это отдельный вопрос платформенной реализации;
- изменения в окружениях со статусом `Untrusted` запрещены.

Разделение на `plan` и `apply` легко добавить сейчас как имя в контракте и дорого вставлять потом: пользователь увидит план до того, как система изменится.
