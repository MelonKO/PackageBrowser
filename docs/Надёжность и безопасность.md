# Надёжность и безопасность

> Оригинальная серия: [[Package Browser]]

## Зачем об этом думать

Самый важный риск здесь не нагрузка, а то, что приложение запускает чужие программы: менеджеры пакетов, провайдеры плагинов и исполняемые файлы внутри проектов. Поэтому надёжность и безопасность тесно связаны: оба вопроса про границу доверия между ядром и всем, что оно запускает.

Масштабирование вертикальное: одна машина, один настольный процесс, без репликации и failover. Политика отказа — «показать устаревшее с пометкой», а не «падать».

## Пример: чужой проект с `.venv`

Вы добавили корень `~/downloads`, в котором лежит чужой проект с `.venv`. Приложение нашло `.venv/bin/pip`. Если просто выполнить `pip list`, будет запущен файл из скачанного каталога, то есть чужой код с вашими правами. Поэтому по умолчанию окружение читается разбором файлов (`*.dist-info/METADATA`), без запуска чего-либо, а запуск инструмента из проектного каталога разрешён только в корнях, которые вы пометили как доверенные. Для остальных окружение получает статус `Untrusted`: пакеты видны, запуск запрещён.

## Правила

| Предмет | Правило |
| --- | --- |
| Изоляция сбоев | провайдер в своём процессе; падение, зависание или мусор в stdout не затрагивают другие плагины и хост |
| Таймауты и лимиты | на каждый запрос — дедлайн и максимальный размер вывода; стартовые значения нужно подобрать замером на реальных менеджерах, я не называю числа без измерений |
| Параллелизм | ограниченный пул одновременных процессов; один медленный менеджер не занимает все слоты |
| Кэш | UI всегда читает SQLite, а не провайдеры: зависание плагина никогда не замораживает интерфейс |
| Частичные данные | список с `complete: false` или ошибка окружения показываются в UI, предыдущие данные в кэше не затираются |
| Запуск процессов | только с массивом аргументов, без оболочки; подстановки в шаблонах команд манифеста проверяются по белому списку (`{exe}`, `{tool}`, `{root}`) |
| Доверие к проекту | запуск инструмента из каталога проекта только в доверенных корнях (по аналогии с workspace trust в редакторах кода); в остальных — только чтение файлов, окружение получает `Untrusted` |
| Сторонние плагины | установка плагина с исполняемым провайдером = исполнение кода от имени пользователя, поэтому нужно явное подтверждение; декларативные манифесты безопаснее, но тоже задают команды |
| Приватность | приложение само не делает сетевых запросов; списки пакетов никуда не отправляются |
| Диагностика | логи через `QLoggingCategory` по каждому плагину; экран плагинов показывает последнюю ошибку и время последнего запроса |

> [!note]
> Подпись плагинов в MVP не нужна. Подтверждение при установке плагина с исполняемым провайдером остаётся.

## Состояния плагина

Сбои плагина не должны превращаться в сбои приложения. Для этого у плагина есть жизненный цикл с карантином (`Failed`, `Quarantined`), описанный в [[Плагины и JSON-RPC]]: после нескольких неудачных перезапусков плагин отключается до ручного включения, а данные его окружений помечаются неактуальными.
